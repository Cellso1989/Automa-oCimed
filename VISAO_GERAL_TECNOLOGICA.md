# Visão Geral Tecnológica — Automação CIMED

## Visão Geral Resumida

O projeto Automação CIMED automatiza a validação ponta a ponta dos principais fluxos de negócio do Salesforce (Lightning) da Cimed no ambiente UAT — criação e conversão de Leads, cadastro de Contas/Contatos, Oportunidades e Pedidos (inclusive via Visita/Organizer) — cobrindo desde a interface até a integração de retaguarda com o SAP. O ecossistema foi montado em torno do **Playwright** com **TypeScript/JavaScript**, escolhido por rodar de forma estável neste ambiente (uma tentativa anterior com Cypress travava por limite de memória do Electron), combinado com login via **API SOAP** para contornar o reCAPTCHA da tela de login, consultas **SOQL** diretas à API REST do Salesforce para validar dados que a UI não expõe, execução automatizada em **GitHub Actions (CI/CD)** e um conjunto de **skills e scripts assistidos por IA** que aceleram tarefas repetitivas do dia a dia do QA (aprovar Lead, gerar massa, diagnosticar falha de integração, converter chamados do Jira em specs). O resultado é uma suíte enxuta, orientada a dados reais de negócio, com foco em estabilidade acima de cobertura por volume.

## Tabela de Arquitetura e Tecnologias

| Tecnologia/Ferramenta | Categoria | Função no Projeto | Explicação Simplificada |
|---|---|---|---|
| **TypeScript / JavaScript** | Linguagem | Linguagem em que specs, helpers e scripts são escritos | É o "idioma" em que todo o código do projeto é escrito — o mesmo usado por boa parte da web moderna. |
| **Playwright (`@playwright/test`)** | Automação Frontend / Framework de Testes | Motor que abre o navegador, interage com a tela do Salesforce e valida o comportamento esperado | É o "robô" que clica, digita e navega pela tela como um analista faria manualmente, só que de forma repetível e rápida. |
| **Page Object Model (POM) via helpers (`support/`)** | Padrão de Projeto / Arquitetura | Centraliza em `support/leadHelpers.js`, `massaHelpers.js`, `lookup.js`, `userHelpers.js` a lógica de interação com telas e fluxos reutilizados por vários testes | Em vez de cada teste repetir "como preencher a tela de Lead", existe um único lugar que sabe fazer isso — os testes só chamam essa função pronta. |
| **Fixtures customizadas (`support/fixtures.js`)** | Automação Frontend / Reuso | Fornece uma `page` já autenticada no Salesforce e uma `sfSession` para chamadas diretas à API, prontas para qualquer spec importar | É um "atalho" que já entrega o navegador logado para o teste, sem cada um precisar repetir o processo de login. |
| **Login via API SOAP (`support/soapLogin.js`)** | Integração / Autenticação | Autentica no Salesforce por trás dos panos (`frontdoor.jsp`), sem passar pelo formulário de login normal | Contorna o reCAPTCHA invisível que costuma barrar navegadores automatizados, autenticando "por fora" da tela de login. |
| **SOQL via API REST (`support/soqlQuery.js`)** | Integração / Validação de Dados | Consulta dados do Salesforce que não aparecem na interface (ex.: Tipo de Registro, `IsConverted`, `Status_Integracao__c`) | É como fazer uma "busca no banco de dados" do Salesforce diretamente, quando a tela não mostra a informação necessária. |
| **Integração SAP (via campos `Status_Integracao__c` / `Log_Integracao__c`)** | Integração de Backend | Valida se o cadastro de Conta criado pelo fluxo de Lead foi aceito pelo sistema SAP | Depois que o "cliente" é criado no Salesforce, o sistema avisa se o SAP (retaguarda financeira/fiscal) aceitou ou rejeitou esse cadastro. |
| **GitHub Actions (`.github/workflows/playwright.yml`)** | CI/CD | Executa a suíte automaticamente a cada push na `main`, instala dependências, roda os testes e salva screenshots de falha | É a "esteira" que roda os testes sozinha sempre que o código muda, sem precisar de alguém rodando na mão. |
| **GitHub Secrets** | Segurança / Configuração | Armazena credenciais (usuário, senha, token do Salesforce, credenciais do Jira) fora do código, injetadas em tempo de execução no CI | Guarda as "chaves de acesso" num cofre do GitHub, para que nunca fiquem expostas no código-fonte. |
| **`env.json` (local, fora do controle de versão)** | Configuração | Fornece as mesmas credenciais/URLs ao rodar os testes localmente | É o equivalente local ao cofre de secrets do CI — cada máquina tem o seu, sem subir para o repositório. |
| **Reporter `list` do Playwright** | Relatórios | Mostra no terminal, em tempo real, quais testes passaram ou falharam | É o "placar" que aparece na tela enquanto os testes rodam. |
| **Screenshots automáticos (`screenshot: "on"`)** | Relatórios / Evidências | Captura uma imagem da tela a cada passo, salva por tema em `tests/<Tema>/screenshots/` | Tira uma "foto" da tela durante o teste, útil para provar o que aconteceu ou investigar uma falha. |
| **Projects do Playwright (por tema)** | Automação Frontend / Organização | Separa a suíte em grupos (Login, Lead, Oportunidade, Pedido, Conta, Contato), cada um com sua própria pasta de testes e evidências | Organiza os testes em "gavetas" temáticas, para rodar só o que interessa e manter as evidências separadas por assunto. |
| **API do Jira (`scripts/jira-fetch-tasks.js`)** | Integração / Gestão de Tarefas | Busca chamados atribuídos ao analista no projeto SFQA para gerar rascunhos de specs automaticamente | Conecta o projeto de automação com o quadro de tarefas do time, trazendo os chamados pendentes para dentro do fluxo de QA. |
| **Agentes de IA (Claude Code + skills do projeto)** | Assistência de QA / Produtividade | Orquestram tarefas de ponta a ponta: criar/converter Lead, aprovar etapas como usuário específico, diagnosticar falha de integração com o SAP, converter chamados do Jira em specs | Funcionam como um "analista assistente" que executa tarefas repetitivas e bem definidas do dia a dia de QA sob comando, sempre com aprovação humana antes de qualquer ação sensível. |
| **`docx` (biblioteca Node)** | Documentação | Disponível no projeto para geração programática de documentos Word | Permite montar relatórios/documentos formatados automaticamente a partir do código, quando necessário. |

## Fluxo de Trabalho (Como tudo se conecta)

1. O analista escreve ou ajusta um **spec Playwright** em `tests/<Tema>/`, reutilizando helpers já existentes em `support/` sempre que possível (Page Object Model).
2. Ao rodar o teste (`npx playwright test "CT X"`), a **fixture customizada** (`support/fixtures.js`) autentica automaticamente via **login SOAP**, evitando o reCAPTCHA da tela normal, e entrega uma `page` já logada no Salesforce.
3. O teste executa as ações na interface (Lightning) usando **locators estáveis do Playwright** (`getByRole`, `getByLabel`, etc.), seguindo os fluxos de negócio reais (ex.: criação de Lead, aprovação de etapa, conversão em Conta).
4. Quando a validação não pode ser feita só pela tela (ex.: confirmar `IsConverted` ou `Status_Integracao__c`), o teste consulta o Salesforce diretamente via **SOQL/API REST**.
5. Durante a execução, o Playwright captura **screenshots** automaticamente, salvos na pasta do próprio tema.
6. Localmente, o QA acompanha o resultado pelo **reporter `list`** no terminal; tarefas repetitivas (aprovar como outro usuário, gerar massa de dados, diagnosticar falha de integração, transformar chamado do Jira em spec) podem ser delegadas às **skills de IA** do projeto.
7. A cada push na `main`, o **GitHub Actions** repete esse mesmo processo em ambiente limpo (Ubuntu), usando credenciais guardadas em **Secrets**, exclui testes com limitações conhecidas (ex.: Hospitalar sem processo de aprovação ativo) e publica os screenshots de falha como artefato para investigação.
8. Falhas são analisadas com base nas evidências (screenshot, stack trace, estado da URL/DOM) para classificar a causa — bug de aplicação, problema de automação, dado de massa ou limitação estrutural do ambiente — antes de qualquer correção.

## Benefícios da Escolha

- **Estabilidade sobre um ambiente historicamente instável**: Playwright substituiu o Cypress após travamentos de memória, e o login via API SOAP elimina falhas de autenticação causadas pelo reCAPTCHA — reduzindo flakiness na raiz em vez de mascará-la com esperas artificiais.
- **Validação além da interface**: combinar UI (Playwright) com consultas diretas via SOQL/API garante que os testes verifiquem o resultado de negócio real (conversão de Lead, integração com o SAP), não só o que aparece na tela.
- **Baixo custo de manutenção**: a centralização de lógica em helpers reutilizáveis (`support/`) e a organização por tema (`projects` do Playwright) tornam mais simples localizar, ajustar e rodar apenas o que é necessário, sem repetir código entre specs.
- **Ciclo de feedback rápido e assistido**: a integração com GitHub Actions garante execução contínua sem depender de máquina local, enquanto as skills de IA aceleram tarefas manuais repetitivas do QA (massa de dados, aprovações, diagnóstico de integração), liberando tempo para investigação e cobertura de cenários novos.
